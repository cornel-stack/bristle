## Overview

This slice ships the Tier 2 build-plan slice **2.5 — Changelog**. Two new surfaces land: a Changelog page at `/changelog` (replaces the slice-005 `<ComingSoon version="0.2.5" />` stub) and an Atom 1.0 feed at `/changelog.atom`. The page reads top-to-bottom as a dated release-notes log: top nav + `ChangelogHero` (eyebrow `CHANGELOG` + serif headline `What's new in Bristle.` + subhead `Public, dated, attributable. The shape of our pace.`) + two-column body (left = `ChangelogJumpNav` sticky month list + `RssSubscribeCard`; right = 5 `ChangelogMonthSection`s with 11 `ChangelogEntry` items across them) + site footer. Each entry is a three-column row at md+ (left = abbreviated date; middle = title + type badge + body paragraph; right + below = optional figure), stacking to single-column at mobile. Each entry's outer `<article>` carries `id="entry-{slug}"` for permalink anchoring + `data-changelog-month="{monthKey}"` so the rail's `IntersectionObserver` can resolve which month section is in view. The `ChangelogJumpNav` is the **fourth** structural mirror of the same IO + topmost-visible + no-flicker + reduced-motion + modifier-key-passthrough + mobile-pill auto-scroll pattern (slice-006 FAQ rail, slice-009 Legal TocRail, slice-010 Blog rail, now slice-011 Changelog jump-nav); the tracked follow-up to extract a shared `SectionScrollSpyRail` now spans 4 implementations and is the highest-pressure refactor item. The `RssSubscribeCard` sits below the rail and links to `/changelog.atom` — the only feed format shipped this slice (no separate RSS 2.0 endpoint; the `RSS · ATOM` eyebrow is recognition typography). The Atom feed is a Next.js Route Handler at `apps/web/src/app/changelog.atom/route.ts` that hand-rolls valid Atom 1.0 XML (template strings with XML-entity escaping for entry titles/bodies — no XML library dependency). The page is statically prerendered (`○ Static`); the feed handler is `force-static`-ed where Next.js allows to keep the response sub-1ms. **One** "Current" pill renders across the 5 month sections — on whichever month contains the entry with `max(date)` — computed at build time from the data store, no runtime `Date.now()`. **Zero new top-level dependencies. Zero edits to slice-005/006/008/009/010 files** other than the wholesale rewrite of `/changelog/page.tsx` (the same FR-001-style precedent slice 010 used for `/blog/page.tsx`).

### User Story 1 - A visitor browses the changelog and navigates between months (Priority: P1)

A visitor clicking `Changelog` in the slice-005 top nav (or in the site footer's Product column, or following an inbound link from a release announcement) lands on `/changelog` and sees the full editorial release log per `design/Public_pages.pdf` page 8: editorial hero (eyebrow + serif headline + subhead), two-column body — left column is a sticky vertical jump-nav listing 5 months (`May 2026` / `April 2026` / `March 2026` / `February 2026` / `January 2026`) plus an `RssSubscribeCard` below it; right column is the 5 month sections with 11 entries total. ### User Story 2 - A visitor subscribes to changelog updates via Atom (Priority: P1)

A visitor who reads `Public, dated, attributable. The shape of our pace.` and wants to follow the changelog without remembering to check looks for a feed. They see the `RssSubscribeCard` in the left rail under the jump-nav: `RSS · ATOM` eyebrow + `Subscribe to /changelog.atom from anywhere.` with `/changelog.atom` rendered as an inline link. They click the link (or copy the path into their reader of choice — NetNewsWire, Feedbin, etc.). They get a valid Atom 1.0 XML response listing all 11 changelog entries with proper feed-level metadata + per-entry permalinks. Their reader subscribes; the next entry that lands shows up automatically.

Feed-discovery tools (browser feed-reader plugins, sharing tools, NewsBlur) also find the feed via the `<link rel="alternate" type="application/atom+xml" href="/changelog.atom" title="Bristle changelog feed">` element in `/changelog`'s `<head>` — no user click required for these tools.

**Why this priority**: The Atom feed makes the changelog a first-class subscribable artifact rather than a passive page. For the bootstrapped indie persona who already uses RSS readers (overrepresented vs the general population), the feed turns "I should remember to check Bristle's changelog" into "Bristle's changelog shows up where I already read." P1 alongside US1 because it's a small surface that materially affects the changelog's reach.

**Independent Test**: `curl -i <local>/changelog.atom` on a production build. Confirm HTTP 200 with `Content-Type: application/atom+xml` (or equivalent — the framework may add `; charset=utf-8`). Inspect `/changelog`'s `<head>` and confirm the `<link rel="alternate" type="application/atom+xml">` element is present. Open the page in any browser that supports feed auto-discovery; confirm the browser surfaces the Atom feed.

### Edge Cases

- **Deep-link to an entry** (`/changelog#entry-slack-delivery-for-alerts`): the browser performs its native anchor-jump scroll on page load; the `ChangelogJumpNav`'s `IntersectionObserver` fires the moment the entry's parent month section enters the viewport and marks that month active. The rail's active state matches within ~100ms of load.
- **`ChangelogJumpNav` "between months"**: when the visitor is scrolled to a position where no month section's marker element is intersecting (e.g. between the bottom of April and the top of March), the rail keeps its previous `active` value — no flicker, no "no-month" intermediate state. Same rule as slices 006 / 009 / 010 rails.
- **Single-entry-per-month case**: if a month ever ships with just one entry (e.g. a slow December), the `ChangelogMonthSection` still renders with its `<h2>` + the lone entry. The `Current` pill rule (max(entry.date) → matching monthKey) handles single-entry months correctly — the lone entry is both the max and the only one.
- **`Current` pill on retroactive content edits**: the pill is computed at build time from `max(entry.date)`. If a founder edits an older entry's content but doesn't change its date, the pill stays on the current month. If a founder updates an entry's date (or adds a new entry with a later date), the pill follows automatically on the next build. No runtime `Date.now()` — pure compile-time data.
- **Reduced-motion at runtime**: the `prefers-reduced-motion` media query is read on each `scrollIntoView` invocation, not cached at component mount, so a user toggling the OS preference mid-session takes effect immediately on the next jump. Same pattern as slices 006 / 009 / 010.
- **Mobile pill row at narrow widths (320)**: the horizontal pill row scrolls horizontally inside its own container; the active pill auto-scrolls into view (`scrollIntoView({inline: "center", block: "nearest"})`) so the visitor always sees which month they're in. Instant under reduced-motion.
- **Visitor reads to the bottom of the page**: the last month (January 2026) becomes active and stays active as the visitor scrolls past it; the rail does not unset.
- **Browser without `IntersectionObserver`** (none in target support — Safari 12.1+ baseline since 2019): the `ChangelogJumpNav` still renders as static anchor links; the active-state tracking degrades silently to "no active state" — anchors still work (native browser anchor navigation), just no rail-side highlight. No JavaScript error.
- **Atom feed XML-escaping correctness**: entry titles like the April 22 entry (which contains literal `"yesterday"` quotation marks) must be escaped as `&quot;yesterday&quot;` in the feed body so a strict XML parser accepts the output. Bodies containing `&` (none currently, but future entries may) must be escaped as `&amp;`. The feed's escaping function handles `<`, `>`, `&`, `'`, `"` at minimum.
- **`/changelog.atom` cache behavior**: the `Cache-Control: public, s-maxage=3600` header means Vercel's edge holds the response for up to 1 hour between revalidations. Acceptable freshness for a changelog feed (which updates on a per-deploy cadence, not per-second). Subscribers' RSS readers typically poll every 1-4 hours, so the edge cache is transparent.
- **Feed update timing**: the Atom feed's content reflects whatever `BLOG_ARTICLES`-equivalent (`CHANGELOG_ENTRIES`) is in `apps/web/src/components/changelog/changelog-entries.ts` at build time. When the founder adds a new entry, the next deploy regenerates both the static HTML at `/changelog` AND the static XML at `/changelog.atom` together — they cannot drift.
- **Browsers that don't support `<link rel="alternate" type="application/atom+xml">` auto-discovery** (most modern browsers don't — Firefox removed it in v64, Chrome never had it built-in): the `<link>` element is still present in `<head>` and still consumed by feed-reader extensions (Feedly Subscribe Button, RSS Feed Reader by Inoreader, etc.), so the auto-discovery affordance works for visitors who use those tools.
- **Future RSS 2.0 endpoint**: deliberately not shipped this slice. The rail's `RSS · ATOM` eyebrow is recognition typography (visitors who don't distinguish formats see the familiar `RSS` glyph; visitors who do see `ATOM` and know the modern feed format is available). If a future visitor explicitly requests `/changelog.rss` or `/feed.xml`, those routes resolve to Next.js's default 404 — documented carry-forward.

## Requirements *(mandatory)*

### Functional Requirements

**Routes (US1, US2, US3)**

- **FR-001**: The slice-005 soft-404 stub at `apps/web/src/app/changelog/page.tsx` (`<ComingSoon version="0.2.5" />`) MUST be replaced wholesale with the full Changelog page. The handler is an async function that returns a `Response` with body = hand-rolled Atom 1.0 XML serialized from `CHANGELOG_ENTRIES` + headers `Content-Type: application/atom+xml; charset=utf-8` and `Cache-Control: public, s-maxage=3600`. The handler MUST attempt `export const dynamic = "force-static"` (per plan-time decision §"render mode for /changelog.atom").
